# Правила работы над Болотной рыбалкой

## Начало любого нового чата

1. Прочитай [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) — это переносимая память проекта: принятые решения, история, архитектура, проверки и деплой.
2. Прочитай [README.md](README.md) для запуска и игрового цикла. Для интерфейса дополнительно прочитай [DESIGN.md](DESIGN.md), для графики — описания в `src/art/`, для звука — `src/audio/README.md`.
3. Проверь `git status`, текущую ветку и относящийся к задаче код. Не считай старую запись в контексте доказательством текущего состояния VPS или рабочей копии.
4. Сначала ищи уже известные ответы в этих файлах. Не проси пользователя заново объяснять стек, путь на VPS или способ запуска, если они здесь описаны.

Этот файл и `PROJECT_CONTEXT.md` должны оставаться в Git и работать после клонирования на другой компьютер. Для продолжения проекта доступ к прежним чатам Codex не обязателен.

## Как выполнять работу

- Отвечай по-русски. Порученную реализацию доводи до готовности и проверки; обычные обратимые решения принимай самостоятельно.
- Новые сообщения во время работы учитывай как уточнения текущей задачи, если пользователь явно не отменяет её.
- Соблюдай существующий стек и художественное направление. Выбирай минимальный подходящий набор навыков; не вводи новый движок, дизайн-систему или зависимости без причины.
- При разрешённой работе с субагентами делегируй только независимые задачи. Само наличие нескольких файлов не требует делегирования.
- Не меняй выбранную модель, режим или лимиты без основания в поручении.
- Не перезаписывай чужие изменения. Перед перезапуском локального сервера установи, что процесс и база принадлежат этому проекту.
- Коммит и push выполняй по поручению пользователя. Деплой на VPS не следует автоматически из разрешения на push. По текущей договорённости команды на VPS выполняет сам пользователь.

## Что сохранять в контексте

Перед финальным ответом по каждой значимой задаче обновляй `PROJECT_CONTEXT.md`:

- Что попросили и какой результат получился; почему выбрано решение, если это влияет на дальнейшую разработку.
- Какие механики, интерфейсы, файлы, команды запуска или настройки изменились.
- Что проверено фактически, с каким результатом; какие ограничения и вопросы остались.
- Какие прежние решения заменены, отменены или отложены.
- Статус доставки: локально, закоммичено, запушено, инструкция деплоя выдана, деплой подтверждён. Это разные состояния.

Обновляй описание текущего состояния, а затем добавляй короткую запись в журнал в конце файла. Для обсуждения без правок достаточно зафиксировать новое решение или существенный открытый вопрос. Не записывай каждое чтение файла и каждую неудачную команду.

Указывай дату в `Europe/Moscow`. Не выдумывай хеш ещё не созданного коммита; историю коммитов можно проверить через Git. По возможности включай контекст в тот же коммит, что и изменение. Не оставляй противоречащие друг другу версии текущих правил.

В финале чата кратко сообщай: что готово, как проверено, что осталось нерешённым, обновлён ли контекст; при порученном коммите, push или деплое — их фактический статус. Пользователь не должен собирать итог из промежуточных сообщений.

## Инварианты проекта

- Сервер определяет улов, правила боя, награды и рейтинг. Клиент не назначает себе рыбу, золото или очки.
- Карточный бой, колода, инвентарь и хаб личные. Соседям передаётся только публичное состояние рыбака. Cookie сессии не является публичным идентификатором.
- Пауза таймера во время боя касается только его участника. Онлайн не должен блокировать действия в карточной игре.
- Сохраняй совместимость профилей SQLite; миграция не должна повторно выдавать награды.
- Координаты лодок, зон, маршрутов и проверки дальности задаются согласованно в `shared/navigation.ts`.
- 3D отложено. Цель в 1000 одновременно играющих пользователей не подтверждена нагрузочным тестом.
- Существующие чужие проекты на VPS не удаляй по старой записи в истории: их текущее состояние и конкретное разрешённое действие нужно установить заново.

## Проверки и данные

- Поведение программы: `npm test`. Сборка и типы: `npm run build`.
- UI: осмотри изменённый экран в доступном браузере; для адаптивных изменений проверь узкую ширину. Не выдавай имитацию или непроверенный скриншот за результат.
- Для чисто текстовых правок перечитай текст, проверь ссылки, команды и `git diff --check`; полный прогон игры без причины не нужен.
- Проверки с тестовыми профилями проводи с отдельным `FISHING_DB`. Пользовательскую `data/fishing.sqlite` не используй как фикстуру.
- Не коммить базы, WAL/SHM, cookies, ключи, токены, пароли, `.env`, логи, `node_modules`, `dist` и сырые выгрузки чатов. Действующий `.gitignore` сохраняй.
- Используй относительные ссылки внутри документации репозитория. Не делай инструкции зависимыми от локальных путей старого компьютера, папки `HarnessAi` или файлов из `.local`.
- Если среда не позволяет выполнить проверку, укажи конкретное ограничение и выполненную альтернативу; не отмечай задачу проверенной без свидетельства.
